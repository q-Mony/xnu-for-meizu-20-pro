# R17 黑屏与启动耗时分析（Sol 直接读取）

2026-10-30。新增文件，无旧版。本轮日志读取、分析均由 Sol 直接执行，未调用 dsh 或子智能体；未改生产代码、未构建或刷入新候选。

手机已从实测 Fastboot A 返回 Android B，只读核对完整 A/B、GPT 与固定暖 Data 输入后，读取 unixnu 末尾 32 MiB 日志。A 为 R17 `8796d6c5…3338d6`，Android B `7df205f1…1745a2` 保持不变。其他设备只在枚举中出现，未向其发送命令。手机最后保持 Android B。

## 结论

1. **黑屏的起因未定案；不能称已修复，也不能认定正常息屏。** 用户明确确认：Hello 先出现，随后纯黑，按键和点屏均不能恢复。保留窗口中没有内核 panic/断言，没有原 libate sbfault，也没有 SpringBoard/backboardd/Setup 的退出记录。窗口持续至内核时钟 500.104294 秒。以上只证明所采集窗口，不能证明所有服务和显示链路正常。
2. **无法唤醒的基础问题已找到：触摸与 HID 初始化在实际编译参数中关闭。** `bsd_init.o.json` 的定义为 `XNU_MEIZU_TOUCH=0`、`XNU_MEIZU_HID=0`，对应源码的初始化调用被条件编译删除。TOML 中 `meizu-touch=4` 不能打开编译掉的功能。`MeizuHidProbe.cpp` 还明确将 `native_buttons_set_sink` 实现为空，板级实体按键驱动未接入。不能用“按了电源/点了屏但没有恢复”来单独证明内核死机；它也不证明变黑一定来自正常待机。
3. **36 秒长等待已定位到 backboardd 收到目标请求之前。** 本轮新的 life 完整记录绑定 SpringBoard pid26/taskgen54/tid254/seq204；实际接收和回复均是 backboardd pid55/taskgen250/tid426，接收 6001009、回复 6001109，全部结果为0。接收前 36.320938 秒；从接收到发送方完成仅 2.138281 毫秒。因此应继续区分服务初始化/接收就绪、launchd端口转交/排队、线程调度等接收前因素，不能把36秒叫作回复处理耗时，也不能直接改超时掩盖。
4. **本轮无法准确给出 Boot 菜单→Hello 首帧用时。** Setup armed 的内核时钟为102.125067秒；其后的第一条已记录换帧为102.290412秒，但没有画面内容，无法证明那帧是Hello。Boot菜单起点也未与该时钟绑定。此前不用手工计时的采集设计仍缺这两个端点，不能用 Setup 启动、任意换帧或用户回复时间代替完整 Boot→Hello。

## 黑屏证据边界

- NegroniFramebuffer.cpp 的 `negroni_fb_swaps_logged < 16` 只打印前16次有效图层提交。本轮恰好16条，最后时钟120.298239秒；不能因之后无swap日志就判定显示停止。
- 当前驱动对不少selector只返回成功/清零输出，没有持续屏幕电源/亮度/黑帧内容记录。因此不能区别：用户态提交黑画面、正常待机但缺输入唤醒、画面传输停滞、控制台覆盖GUI或其他显示故障。
- 驱动源码注释明确控制台默认继续写同一帧缓冲。R17无 `negronifb_noconsole=1`；板级BootLog还接管PE_kputc且会清黑背景/滚屏。这是需验证的另一条覆盖路径，**不是已证明的本次原因**。不能仅添加静默参数就宣称修复。
- 本轮观察到30次identityservices的BRK/退出、4个Poster扩展check-in超时等后台错误；没有证据将这些事件直接等同于Hello黑屏，旧的ASTC故障本轮未复现也不能宣布已修复。
- 用户看到的preoslog提示在持久化文本中未出现；它在debug.c走kprintf路径。该缺失不推翻用户观察，也不能从这里判断它的实际发生次数。

## 仍可提速的具体方向

1. **优先接收前36.321秒。** 新探针已排除“目标handler处理慢”作为这36秒的解释。下一次只补backboardd初始化/注册/接收就绪及有限线程栈/线程状态时间点，关联同一taskgen和reply-port identity，区分初始化晚、launchd转交晚或服务线程晚接收。已有静态分析的FOREVER group waits仍未被排除，不能凭数值直接改30秒定时器或伪造digitizer。
2. **暖Data流式SHA加速是较独立的候选。** NativeRamBlock::warmLoadAdapter仍用普通SHA256_Init/Update/Final；corecrypto实际构建 `CC_USE_ASM=0`，默认descriptor返回软件实现。之前的native_sha256_digest只在签名/根盘校验等接入，未覆盖这份231MB编码输入及512MB逻辑镜像的流式哈希。可在保持逐字节摘要、取消/超时和失败拒绝行为的前提下，复用已有CPU特性检查/抢占保护的硬件压缩路径；不能删除验证或把每4KiB分段单独求摘要后拼接。8.666秒是本轮已测哈希成本，不是承诺能全部节省的时间。
3. **19.288秒签名预处理需减少重复工作/读取。** 硬件SHA已在native签名路径启用，不应再把它误认成未加速；继续增大I/O块不能消除接收前等待。
4. **精确Hello计时需要补端点。** 记录Boot菜单选中/加载开始的计数器并传给内核；记录并保存可验证为Hello的实际首帧证据（或可信的用户态Hello可见回调）。一般first-swap、first-nonblack、Setup armed均不能自动等同Hello。可先用首帧附近的有限图像快照离线核对，避免继续要求用户分段计时。
5. **黑屏应先补显示/输入状态，不能盲开驱动。** 长时间保留低频换帧/成功拷贝/内容摘要及blank/电源状态，记录触摸/HID是否实际启动及事件计数；再做同基线对照。开启现有触摸代码前仍需审查其硬件初始化失败退出和时间成本；实体按键也需要板级接入，不是加一个boot arg就会有。

本轮只完成定位与分析，未制作或安装下一候选；仍遵守用户“改完等待明确安装命令”。
