# R16 日志分析与 R17 本地验收

新文件，无旧版。Sol 已验收 dsh 的实际差异、测试日志、完整构建和镜像；R17 未安装，设备最后确认留在 Android B。

本轮显示查询 6001009 用时 **36.395740 秒**；根设备准备 **16.266393 秒**，根盘挂载 **0.018168 秒**，SystemOS 准备 **0.155406 秒**，Data 准备 **0.005920 秒**。根盘读取累计约 **8.747304 秒**。这些统计范围不同，存在重叠，不能相加作为总启动时间。本轮未进入 Hello；Boot→苹果约80秒是用户观察。

原始 R16 生命周期日志在真实编码器、默认 sid0、loc_size4 配置下稳定触发同一个 `log_encode.c:120` 断言：偏移244，容量250，含头部需要252。R17仅把生命周期和崩溃基础记录先用有边界检查的 snprintf 格式化，再单次 printf("%s") 输出。字段和生命周期逻辑保持不变。56组修复后样例通过，ASan/UBSan无报告；50组可比较的完整文本逐字节一致，另6组旧版会断言。

独立复核6186文件仅两项允许改动，两个实际ARM64编译对象与完整构建一致；受保护对象与冻结R16记录一致。96MiB镜像SHA256：`8796d6c5824ce563fda8b4d0e1a429f235749254648cc160534e5807283338d6`。

硬件日志没有保存panic全文或内核调用栈。本地复现证明该诊断缺陷，但不能独自确认真机当时具体打印调用点。报告中的caller是_Assert调用_panic的有效代码返回地址，并非原始printf调用点；执行器报告写“not a code PC”不够准确，以此澄清为准。

原36秒显示查询等待与ASTC故障仍待解决；R17用于恢复可靠诊断，不宣称提速。下一轮经用户新的安装命令后验证能否正常进入Hello，并读取生命周期接收/回复事件与故障寄存器，继续拆解等待。
