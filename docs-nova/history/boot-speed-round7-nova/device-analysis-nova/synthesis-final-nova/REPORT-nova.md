# 第七轮启动耗时实测

最大的明确服务启动区间是 **SpringBoard 成功 exec 捕获 → 首次 Setup 启动捕获，152.523993 秒**。这不是 Hello 首帧时间。launchd → SpringBoard 为21.108157秒；根设备查找为7.385559秒，根卷/SystemOS/Data几个明确准备调用分别只需0.018273/0.155146/0.005491秒。

| 区间或阶段 | 经过秒数 | 原始日志证据 |
| --- | ---: | --- |
| launchd → SpringBoard 捕获点 | 21.108157 | L239 → L702 |
| SpringBoard → Setup 捕获点 | 152.523993 | L702 → L2762 |
| lsd → Setup 捕获点 | 146.035656 | L893 → L2762 |
| 根设备查找 | 7.385559 | L102 → L137 |
| 根卷挂载调用 | 0.018273 | L138 → L157 |
| SystemOS 准备 | 0.155146 | L178 → L211 |
| Data 准备 | 0.005491 | L212 → L227 |

各启动捕获点只表示成功 exec 后被探针捕获，不表示服务 ready。lsd → Setup 包含在 SpringBoard → Setup 内，不能相加。明确阶段包含 begin 日志开销，也不等于纯函数 CPU 时间。

截至原始L6206，201次日志写入全部返回成功，累计写盘0.360893125秒、复制0.015657239秒、完整尝试0.377318854秒；单次写盘最大0.040944322秒。copy/write已包含在attempt中，三项不能相加。该计量不包括报告printf等全部诊断开销。

最大相邻日志标签间隔只有5.879495秒（L105→L106），位于根设备查找期间。后续heartbeat持续输出，会把长服务等待切成很多短标签间隔，因此gap榜不能替代服务阶段计时。

后段等待链的CPU和IPC细节分别见上级lsd-timing-nova与storage-logio-nova报告。现有证据将排查重点收窄到SpringBoard等待lsd、lsd与containermanagerd/launchd的反复通信；不能仅凭接口非零返回或累计trap时长认定业务失败/串行独占耗时。下一步应定位这条链中重复通信的触发条件与完成事件，而不是继续盲目扩大UFS读块。

本轮保留6270个有效CNTVCT标签，均为19.2MHz，无倒退，首末覆盖218.12409828125秒。这个范围不是Boot→Hello；Boot菜单点击与首次Hello仍无视觉锚点。console ring没有覆盖、无NUL；sbipc自身环另有丢弃/覆盖267031条，故不能声称所有事件完整。

原始L102的根设备begin前有另一条未换行消息。第二个完整P标签明确界定了完整begin；已修正离线解析并通过29项测试和独立复核，最终4个阶段完整、解析issues=0。原始日志、最初解析和修正版解析均保留；未为修解析而改内核或再次刷机。

设备已返回Android B；A仍为第七轮候选96fc4223…303d2c，B原哈希不变。用户确认到Hello，但没有给出秒表总时间。本报告不声明第七轮提速。
