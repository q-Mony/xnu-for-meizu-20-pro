# R8 Data capture and future warm-seed feasibility

2026-10-30, Nova. The Data capture implementation and local verification are complete. This subtask changed only `NativeRamBlock.cpp`, added `WarmCapture.h`, and wrote its own test/report artifacts. It did not access the phone, start a complete kernel build, change persistence mode, mount an image, or implement restoration. Parent owns trigger integration, whole-kernel build, packaging and device operations.

**Result:** the experiment can capture the current RAM Data block contents for offline analysis. Whether those contents can safely become a warm seed, and whether that reduces Boot→Hello, remains unproved until a real capture is checked and a separate restoration experiment succeeds.

**Why this is the next useful experiment.** The fixed R6/R7 packages use byte-identical 512 MiB logical Data seeds: DBRDISK1 with 8 extents, 1,507,488 encoded bytes, encoded SHA-256 `0f1a60ef3e23e355cec56d6a860db5606e2da14cba51660318422efdd99f7c46`, logical SHA-256 `373880d1f64695c6ba71db05354b019cbfe11d253d32427b8d493bcc085981b3`. Both set `ephemeral-storage=1`, omit Data persist/reset boot arguments, and operate in mode 0. Runtime Data writes therefore disappear at the next boot. R6/R7 create `.csstore` under different InternalDaemon container identities and both reach 3,838 measured container receive completions. This supports investigating repeated initialization, but does not prove every request is redundant or predict a speedup.

The prior R7 storage analysis measured root-device readiness at 7.386 s and root I/O read time at 7.486 s; within the observed approximately 91-second lsd interval, root read time was 0.920 s and log-write attempt time was 0.059 s. Overlapping counters must not be added. These observations do not support blaming that entire interval on UFS throughput. Detailed evidence is in [R7 storage report](<nova-root>/artifacts-nova/boot-speed-round7-nova/device-analysis-nova/storage-logio-nova/REPORT-nova.md), [R8 collected evidence](<nova-root>/artifacts-nova/boot-speed-round8-nova/data-cache-path-nova/evidence-nova.json), and the parent's R8 symbolication report.

**Implementation.** [The C entry](<nova-root>/unixnu-main-nova/drivers/NativeRamBlock/NativeRamBlock.cpp:512) requires `nova-data-capture=1`, `native-ufs-partition=unixnu` and a nonzero capture ID. A compare-and-swap permits one enabled attempt per boot. The target is retained only when the experiment is enabled and normal UUID-based Data selection returns one unique NativeRamBlock provider. A conflicting second target is refused. Default disabled boots do not retain a capture target.

[captureWarm()](<nova-root>/unixnu-main-nova/drivers/NativeRamBlock/NativeRamBlock.cpp:97) allocates 132 KiB before locking the existing Data gate. Under that gate it requires online/ready, attached mode-0 sparse Data, successful owner Data preparation, no direct/overlay mode or persistence state, size at most 512 MiB, an already-open 256 MiB export window, and an unchanged GPT. It then serializes nonzero pages using the existing DBRDISK1 layout, complete payload SHA-256 and the committed header described in [PROTOCOL-nova.md](<nova-root>/artifacts-nova/boot-speed-round8-nova/data-cache-path-nova/PROTOCOL-nova.md). There is no allocation, service callback or explicit diagnostic print in this locked method. It releases the gate before logging one `NOVA-DATACAP result` record containing capture ID, status, logical/encoded bytes, extents, start/end/frozen ticks and uncertain-header state.

The preexisting Data gate serializes the source block I/O. Serialization completes before unlocking; the completion log is emitted afterward. This is a block-device cut, not a clean filesystem/application snapshot. In-flight higher-level transactions and dirty buffers may not be committed. Read-only fsck and mounting can only validate the properties those tools check; they cannot certify LaunchServices/container database semantic consistency. A future warm boot must retain normal service validation/rebuilding and cold-seed fallback.

**Runtime limit.** Capacity and allocation are bounded; elapsed time has no total deadline. Source scanning, hashing and up to 2,048 payload writes take place with Data blocked. A host write can wait up to its 2-second command timeout; a sync can wait up to 10 seconds, and host-lock scheduling adds delay. The capture stops on a reported failure and makes the documented cleanup attempt, but successful commands near their limits can accumulate a long freeze. `frozen_ticks` and start/end must be inspected on the real device. The parent schedules this one-shot capture 90 seconds after the first Setup arm. Setup execution is not a Hello display timestamp: verify that actual Hello preceded capture before treating capture overhead as outside the Boot→Hello measurement. Capture itself is not a speed optimization.

**Conditions for a later warm-seed candidate.** The current capture only provides an analyzable block cut. Before it becomes input to another experiment, the reader must bind the exact full-window dump to the matching successful current-run acknowledgement, old logical-seed hash, new header hash, complete payload hash and known source package. Preserve that original capture, and perform structural APFS/volume checks on a separate copy. Reject structural failures; do not silently repair and relabel the original as clean. Even successful read-only checks do not replace service validation on the next boot.

The current identity chain is precise: [NativeRamBlock start](<nova-root>/unixnu-main-nova/drivers/NativeRamBlock/NativeRamBlock.cpp:296) hashes all logical seed bytes; [native_owner_data_prepare](<nova-root>/unixnu-main-nova/out/meizu20pro/tree/.cache/xnu-work/bsd/kern/kern_exec.c:9377) records this digest and selects the exact configured Data volume UUID, then verifies the actual mounted device, APFS type and writable state. The Data digest is a measured seed identity, not an Apple signature. [native_owner_publish_boot_manifest](<nova-root>/unixnu-main-nova/out/meizu20pro/tree/.cache/xnu-work/iokit/bsddev/IOKitBSDInit.cpp:582) hashes its domain and the already verified root/cache manifest digests and role tags; it does not include the Data digest. The normal startup completes and checks root/SystemOS authorization and boot-manifest publication before Data preparation. Replacing a Data seed therefore does not require fabricating, disabling or rewriting OS/SystemOS signatures or their manifest.

A later offline initrd replacement must use an explicitly revised packer, recompute the new packed and complete logical hashes, record the source OS/build and Data UUID, recalculate all affected file/boot/FAT manifests, and extract/compare the final image. The R8 packer intentionally permits only kernel and capture-argument changes and must reject seed replacement. The same valid Data volume UUID can retain the existing compiled `XNU_OWNER_DATA_VOLUME_UUID`; if the UUID changes it must be derived from the actual volume and the corresponding configuration/header rebuilt. Do not change OS/SystemOS identity to make mismatched Data appear compatible. DarwinBoot writes the actual new PackedRAMDisk memory address and encoded length; NativeRamBlock must import the complete new disk and calculate its identity before `registerService()`, rather than replace an already-probed APFS device late.

Current 90 MiB payload FAT has 18,118,656 free bytes. Adding back the original seed allocation yields at most 19,627,008 bytes for a replacement seed before any new kernel growth. The complete boot image and boot partitions are 96 MiB. An exported warm seed can be far larger than this budget; capture success is not a packaging fit guarantee. Measure the real encoded output before choosing an offline replacement or separately designed early-boot restoration path.

Keep mode 0 and the existing AKS/ephemeral behavior for the next controlled experiment unless that behavior is separately designed and tested: current AKS compatibility depends on `storeMode==0 && persistState==0`. Existing mode-1 partial restoration/reset issues in [the earlier feasibility report](<nova-root>/artifacts-nova/boot-speed-round4-nova/device-analysis-nova/data-seed-feasibility-nova.md) remain outside this change. The planned next evidence is lower repeated LS/container work with valid complete restoration, followed by a reproducible reduction of actual Boot→Hello including all additional loading cost. No speed gain has been claimed by this capture subtask.
