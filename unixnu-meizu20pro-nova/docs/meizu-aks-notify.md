# Meizu 20 Pro notification-only KeyStore candidate

This board kit is **off by default**. It publishes a distinct `MeizuKeyStoreNotification` IOService only for an explicitly selected disposable packed RAM Data boot. It provides no `AppleKeyStore` metaclass, user client, selector implementation, lock-state answer, keybag, key, or data-protection capability. Both `newUserClient` overloads return `kIOReturnUnsupported`; a successful matching lookup is only an interest-registration endpoint.

## Exact opt-in

The selected `out/meizu20pro/.config` must include `CONFIG_XNU_MEIZU_AKS_NOTIFY=y`, add `-DXNU_MEIZU_AKS_NOTIFY=1 -I{tree}/kits/meizu20pro` to `CONFIG_XNU_EXTRA_CFLAGS`, and append `-Wl,-force_load,{tree}/build/meizu-aks-notify/libMeizuKeyStoreNotification.a` to `CONFIG_XNU_EXTRA_LD_ARCHIVES`. The defconfig documents the same edits. Regenerate the selected config after editing the defconfig. The builder rejects a partial or inconsistent switch. Add `meizu-aks-notify=1` to the candidate boot's kernel arguments; no default boot has this argument. Do not enable this for production/persistent Data.

`board.toml` invokes `build-meizu-aks-notify.py` last among the board archive builders: it invalidates XNU objects that earlier builders inspect. Keep the post-Data hook before the `Data mount returned` marker so the existing watchdog patch remains independently reversible. In default mode it produces no archive and makes no XNU edit. In selected mode it checks and installs `meizu-aks-notify-xnu.patch` in that board's XNU tree, invalidates its two affected objects, compiles the Meizu class with the existing ARM64 XNU recipe, removes the automatic module constructor, and archives it with a globally callable deferred initializer. The post-Data hook in PID 1 checks the boot argument, successful owner Data mount, exact four-byte `/chosen/ephemeral-storage=1`, a 16-byte `PackedRAMDisk` descriptor, and no UFS persistence mode or RAM block persistence state before metaclass initialization and synchronous publication. It refuses if a real `AppleKeyStore` metaclass or matching service is present.

The stock XNU `IOService::copyMatchingService(IOService::serviceMatching("AppleKeyStore"))` searches instances of the real metaclass. A distinct subclass cannot satisfy that exact search, so the guarded `IOUserClient.cpp` bridge runs after the original lookup fails, accepts only the two-key dictionary (`IOProviderClass=AppleKeyStore` and `IOServiceNotificationUser=true`), and returns the owned Meizu endpoint. It does not alter the plural/iterator lookup or arbitrary property matching. A late real class/provider suppresses the Meizu fallback. `IOService::registerInterest` accepts `gIOGeneralInterest` through `registerInterestForNotifier`, installs an `IOCommand` notification list on the service, and dispatches it via `applyToInterestNotifiers`; no synthetic events are sent here. The service holds its original allocation reference after registration because registry attachment is not an ownership retain.

## Local verification

Run `python3 scripts/test-meizu-aks-notify.py` from the device repository and `python3 scripts/build-meizu-aks-notify.py --tree /Users/ym/unixnu_ports/unixnu-main/out/meizu20pro/tree --verify-only`. The latter applies the patch to copies of the XNU files, compiles the service and both hooks with the board's ARM64 compile records, and checks the transformed archive has no automatic metaclass initializer or AppleKeyStore class symbol. It edits no XNU source or shared build output. The actual default builder also returns without producing an archive.

This verifies compile and source contracts only. A real target boot is needed to establish that `MKBEventsRegister`'s specific matching dictionary takes this bridge and that SpringBoard proceeds; other `libaks`/keybag callers still see failed opens. The kernel build/prelink and phone write are deliberately left to the board owner after review.
